10 things a harness does that a model never will:

(Save this before your next vendor demo.)

1/ Someone writes down what "correct" means before anyone writes a prompt.

  • We start with twenty to sixty real cases and the answer the business already agrees on, checked by hand
  • The person who writes them is whoever knows what wrong looks like, usually a senior analyst, never us
  • From then on every change gets scored against that set, so "does it work" turns into a number you can argue about

2/ It reads from a copy of the data and leaves the real system alone.

  • Read-only access to the reporting database
  • A number that's a day old is fine for almost everything, and it can't take production down
  • Before any prompt we write a data dictionary, and the column descriptions people already have are usually enough to start
  • Trusted context is most of the job. Our lead architect's rule is that documentation is 80% of success, and a better model won't rescue bad context.

3/ It removes names and IDs before the model sees anything.

  • Patient, customer and employee identifiers get masked at the data layer
  • If the masking lives in a system prompt, nobody can audit it
  • It checks who's asking before it answers, and different user groups see different columns.
  • Once it's done properly, a lab changing its training policy next year stops mattering, because there's nothing in the prompt worth training on

4/ It makes every answer fit a fixed shape.

  • Each output has a schema it has to match
  • If it doesn't match, it fails and stops, so a CFO never gets a paragraph of confident prose where a number should be
  • KPIs come from fixed calculations behind the agent, every answer shows its source, and if confidence is low it stops and says so.

5/ It checks every answer automatically.

  • A judge scores each run against the golden set
  • So when a model update lands on a Tuesday, Friday's number doesn't silently change
  • When the score drops, you can see which change caused it
  • Every correction a person makes becomes a new test case, so the golden set and the agent both get sharper from real use.

6/ It keeps a person in charge of anything that writes.

  • The agent suggests and a named person approves
  • It only gets reversible actions until it's earned more
  • One client's PR review agent comments on every diff and has no power to block a merge. Every time an engineer dismissed a comment, we logged the pattern so it wouldn't come back, and the noise dropped week after week
  • It has a hard cap on how many times it can retry before handing back to a person, and that limit is a setting, not code.

7/ It puts a ceiling on spend.

  • On that same agent it's $1 to $3 a review, with a hard cap of $20 a day per seat, and all of it is visible on a dashboard
  • The company that reportedly spent $500 million in a month had no caps anywhere
  • If you can't see token spend per workflow, you'll find out about it from finance when it's too late

8/ It keeps the model swappable.

  • The model sits behind an interface, so changing provider takes an afternoon, and it's the part most likely to be replaced next year
  • Change the prompt, the tool definitions or the model long before you consider fine-tuning anything
  • Everything runs in the client's own environment, never in a vendor sandbox
  • The cloud provider gives you hosting, identity and networking. The harness around your specific workflow is what you have to build yourself, and it's the part competitors can't copy

9/ It records every run.

  • When something comes out wrong, you open the trace, find the step that went sideways, and fix the harness so it doesn't happen again
  • We setup telemetry on every engagement
  • Work starts from an event, like a ticket changing status or a file landing, instead of someone opening a chat window.

10/ It has an owner inside the company.

  • One named person who can change it after we leave, with a runbook
  • The documentation lives in the repository, because the agent reads it and so will the next engineer
  • If nobody is alerted when it breaks, you have a shiny demo
